Grid Editing — Scope & Plan

You keep going back to TablePlus for edits. Two scouts checked ja-db and ten other database GUIs. This is what they found, and a plan that keeps your fast truncated loading.

2. Mistakes to avoid

Each one is a real bug report elsewhere. Each gets a guard.

3. Edit lifecycle

stateDiagram-v2
  [*] --> Browsing
  Browsing --> Editing: F2 on editable cell
  Editing --> Staged: Enter
  Editing --> Browsing: Esc
  Staged --> Editing: edit another cell
  Staged --> Review: Ctrl+S
  Review --> Applying: Enter
  Review --> Staged: Esc
  Applying --> Browsing: all rows matched, committed
  Applying --> Conflict: rowcount not 1, rolled back
  Conflict --> Review: skip, reload or overwrite

5. Apply path

One door: the existing runner chain, so every write reaches the activity log.

sequenceDiagram
  autonumber
  participant UI
  participant API as internal/api
  participant R as Runner chain
  participant DB
  UI->>API: ApplyChanges(ChangeSet)
  API->>R: Do as KindWrite
  R->>DB: BEGIN
  loop each staged change
    R->>DB: UPDATE with bound params, WHERE key and old value
    DB-->>R: rows affected
  end
  alt any count is not 1
    R->>DB: ROLLBACK
    API-->>UI: conflict at row and cell
  else all 1
    R->>DB: COMMIT
    API-->>UI: applied
  end

10. Open questions

  • Is F2 right, or should Enter edit and the viewer move?
  • Ship a per-connection read-only flag in P1 or P4?
  • Old-value guard on edited cells: include, or rowcount only?
  • Tables with no key: read-only, or opt-in user-defined key later?
  • Null-safe equality differs per dialect. SQL Server needs a hook.

Summary

ja-db has no row-write path today, so this is a clean addition behind the existing runner. Stage edits, review the SQL, apply in one transaction, and refuse anything that cannot be addressed by key. Start with the cleanup, because the devserver source is missing from the repo and edits must work on both transports.
